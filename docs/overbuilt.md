# 過剰実装の棚卸し

2026-10-11。**判定は2つの問いだけで行う。**

1. **製品経路が使っているか。**`py/occam.py` から推移的に import されるか
2. **規模が正当化しているか。**実測の件数・時間に対して、その仕組みが必要か

どちらも「無い」なら過剰。片方が「ある」なら保持の理由がある。
**設計の良さは判定に入れない。**よく出来ていることと、必要であることは別。

## 1. 有界メモリの不変条件は、製品が走らせないコードについての主張

**これが最大のものだと思う。**

| | |
|---|---|
| 不変条件 | ピーク RSS が行数に依らない。2軸・2048次元・100万件で実測、データ/RSS = 73倍 |
| 守っている対象 | `engine/` の Rust。KeepOut ロック9箇所のうち5箇所がここ |
| **製品経路からの呼び出し** | **無い。**Python のどのモジュールもエンジンを起動しない |

`py/descriptors.py` と `py/gen_scale.py` はエンジンに言及するが、**定数を合わせるためのコメント**で、
実行はしない。エンジンは `cargo test` と手動でだけ動く。

**つまり、この系の看板である工学的主張は、製品が一度も通らない経路のものである。**

### しかも製品側の律速はメモリではない

今日の実測から。

| | 実測 |
|---|---|
| 掃引の速度 | 100,000分子 / 84.2秒 = **約1,188分子/秒**（RDKit 律速） |
| 27仕様の状態 | **109 KiB** |
| 1仕様の状態 | 4,152 B |

メモリは 109 KiB しか使っていない。**行数非依存性が効き始める規模は、処理速度が先に禁じている。**

| 規模 | 所要時間（1,188分子/秒） |
|---|---|
| 100,000件 | 1.4分 |
| 636,669件（-O 全件） | **9分** |
| 7,805,000件（メモリ試験の x1000） | **1.8時間** |
| ZINC22 全体（約45億件） | **約44日** |

**不変条件は44日かかる規模のために設計され、製品は9分の規模で動いている。**
エンジン側（特徴量を前計算した GBDT）はもっと速いので、不変条件はエンジンにとっては
正当だが、**製品にとっては該当しない。**

**残す理由はある。**M0/M1 の確定値はこれで出ているし、特許の技術開示の中身でもある。
だが「製品の設計上の強み」として語るのは誤り。**別系統である。**

## 2. HyperLogLog スケッチ：約50 KB を持たないために4つの仕組み

| | 実測 |
|---|---|
| 最大の生存数 | 683件（strict 仕様、100,000件読み） |
| 骨格数 | 539件 |
| スケッチの状態 | 4,152 B / 仕様 |

骨格を Python の `set` で**正確に**持つと、539個 × SMILES 文字列 ≒ **数十 KB**。
27仕様で最大規模の仕様（生存 4,304件、骨格 3,772件）まで入れても **2 MB 程度**。

スケッチを使うために付随している仕組みが4つある。

1. HyperLogLog 本体（`sweep.py` の `Sketch`）
2. **uncertain 帯 4.8%**（相対誤差 1.6% の3倍、`propose.py`）
3. **第2パスの正確カウント**（`exact_scaffold_count`、uncertain 帯だけ再読み）
4. **画面で推定と正確を区別する表示**（`render.scaffold_phrase`、今日足した）

**正確な集合を持てば 2、3、4 が全部消える。**しかも判定が常に正確になる。

**スケッチが元を取る条件：**生存数が数百万件に達すること。上の表の通り、その規模は
44日かかる。**つまり現状では元を取っていない。**

ただし1つ留保がある。**固定長であること自体が不変条件3の一部**なので、エンジン側の
主張と地続きではある。`py/sweep.py` は Python なので、エンジンの不変条件には拘束
されない。**そこを分けて考えてよいかは設計判断。**

## 3. 3ビルドのエンジンと、降格済みモジュールへのロック

| | |
|---|---|
| エンジン | 3ビルド（§0.5）。製品からの呼び出しは無い |
| KeepOut ロック | 9箇所。うち `py/candidates.py#lock_0` は**降格済みモジュール** |

`py/candidates.py` は「製品ではない」と宣言されていて `--emit-molecules` なしでは止まる。
**その中の領域を AST ロックで守っている。**守る価値が無いわけではない（SMARTS が
入っている）が、**降格したものを守る構成になっている**のは整理されていない。

## 過剰ではないもの

**これは記録として残す。**上の指摘が「全部削れ」に読まれると困る。

| | なぜ必要か |
|---|---|
| **拒否の仕組み** | 丸めない・読み替えない・推測しない。これが製品の中身そのもの |
| **`knobs.py` の出自管理** | published / relaxation の区別が、提案の監査を1行で可能にしている |
| **positive control** | 重い判定が計算の故障と同じ顔をする問題への唯一の対策（禁忌79） |
| **inert 検出** | 今日 MW 600 が6比較すべてで何も絞っていないことを、頼まれずに報告した |
| **撤回の記録** | §8 に反証された仮説が反証として残っている。これが無い系は信用できない |
| **`provenance.py`** | ライブラリが入力であることの検査。無かったときに逆の結論を出した実績がある |

## 併せて見つかった重複（過剰実装ではなく、禁忌31と同じ形）

**`py/feasible.py` が降格済みの `py/candidates.py` から SMARTS を2つ import している。**

```python
# py/feasible.py:175
import candidates as candidates_mod
"primary_amine": lambda m: m.HasSubstructMatch(candidates_mod.ENTRY_AMINE),
"basic_nitrogen": lambda m: m.HasSubstructMatch(candidates_mod.BASIC_N),
```

同じパターンが `py/knobs.py` にもある（`ENTRY_PRIMARY_AMINE`、`BASIC_NITROGEN`）。
**一級アミンの定義が2箇所にある。**

禁忌31 は「パーサは1つにする — 同じ修復のコピーが `candidates.py` にあり、ブラケット
順序だけ直して価数修正が入らなかった」と書いてある。**同じファイルで、同じ形。**
片方だけ直したときに静かに食い違う。

`feasible.py` を `knobs.py` 側に寄せれば、製品経路から降格済みモジュールへの依存も
同時に消える。
