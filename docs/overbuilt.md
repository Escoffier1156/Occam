# 過剰実装の棚卸し

2026-10-11。**判定は2つの問いだけで行う。**

1. **製品経路が使っているか。**`py/occam.py` から推移的に import されるか
2. **規模が正当化しているか。**実測の件数・時間に対して、その仕組みが必要か

どちらも「無い」なら過剰。片方が「ある」なら保持の理由がある。
**設計の良さは判定に入れない。**よく出来ていることと、必要であることは別。

## 1. 有界メモリの不変条件は、製品が走らせないコードについての主張

**これが最大のものだと思う。**

> **2026-10-12 訂正。この節の前提が誤っていた。**
>
> 「製品経路はエンジンを呼ばない」と書いていたが、**呼ぶ。**
> `py/screenable.py:63` が `ENGINE_FP = ROOT / "engine" / "target-fp" / "release" / "engine"`
> を持ち、`rankability()` が subprocess で起動している。`occam` → `screenable` は
> 製品経路なので、**エンジンは製品の一部**である。
>
> 見落とした原因は私の走査で、`engine/target` という文字列を探したが、実際のコードは
> パス結合（`"engine" / "target-fp"`）で書かれていてその文字列が現れない。
> **文字列検索で「無い」を結論した。**禁忌に足す形。

| | |
|---|---|
| 不変条件 | ピーク RSS が行数に依らない。2軸・2048次元・100万件で実測、データ/RSS = 73倍 |
| 守っている対象 | `engine/` の Rust。KeepOut ロック9箇所のうち5箇所がここ |
| **製品経路からの呼び出し** | **ある。**`screenable.rankability()` が `engine/target-fp/release/engine` を起動し、順位付けの可否を判定する |

`py/descriptors.py` と `py/gen_scale.py` の言及は定数を合わせるためのコメントで、
実行はしない。**起動しているのは `screenable.py` と `m3_order.py` の2本。**

### しかも製品側の律速はメモリではない

今日の実測から。

| | 実測 |
|---|---|
| 掃引の速度 | 100,000分子 / 84.2秒 = **約1,188分子/秒**（RDKit 律速） |
| 27仕様の状態 | **109 KiB** |
| 1仕様の状態 | 4,152 B |

メモリは 109 KiB しか使っていない。**行数非依存性が効き始める規模は、処理速度が先に禁じている。**

| 規模 | 所要時間（1,188分子/秒） |
|---|---|
| 100,000件 | 1.4分 |
| 636,669件（-O 全件） | **9分** |
| 7,805,000件（メモリ試験の x1000） | **1.8時間** |
| ZINC22 全体（約45億件） | **約44日** |

**掃引（RDKit、1,188分子/秒）の律速はメモリではない。**ここは変わらない。

**ただしエンジンは製品経路にいる。**`rankability()` が起動するのは特徴量を前計算した
GBDT で、RDKit の指紋計算を通った後なので、掃引とは別の段である。不変条件はその段に
ついて正当で、**「製品が通らない経路の主張」ではなかった。**

**正確に言うとこうなる。**

| 段 | 律速 | 不変条件の該当 |
|---|---|---|
| 掃引（`sweep.py`、RDKit） | **処理速度**（1,188分子/秒） | 該当しない。109 KiB しか使っていない |
| 順位付けの可否（`screenable.rankability()` → Rust エンジン） | メモリ | **該当する。**ここが不変条件の居場所 |

## 2. HyperLogLog スケッチ：約50 KB を持たないために4つの仕組み

| | 実測 |
|---|---|
| 最大の生存数 | 683件（strict 仕様、100,000件読み） |
| 骨格数 | 539件 |
| スケッチの状態 | 4,152 B / 仕様 |

骨格を Python の `set` で**正確に**持つと、539個 × SMILES 文字列 ≒ **数十 KB**。
27仕様で最大規模の仕様（生存 4,304件、骨格 3,772件）まで入れても **2 MB 程度**。

スケッチを使うために付随している仕組みが4つある。

1. HyperLogLog 本体（`sweep.py` の `Sketch`）
2. **uncertain 帯 4.8%**（相対誤差 1.6% の3倍、`propose.py`）
3. **第2パスの正確カウント**（`exact_scaffold_count`、uncertain 帯だけ再読み）
4. **画面で推定と正確を区別する表示**（`render.scaffold_phrase`、今日足した）

**正確な集合を持てば 2、3、4 が全部消える。**しかも判定が常に正確になる。

**スケッチが元を取る条件：**生存数が数百万件に達すること。上の表の通り、その規模は
44日かかる。**つまり現状では元を取っていない。**

ただし1つ留保がある。**固定長であること自体が不変条件3の一部**なので、エンジン側の
主張と地続きではある。`py/sweep.py` は Python なので、エンジンの不変条件には拘束
されない。**そこを分けて考えてよいかは設計判断。**

### 置き換えを試して戻した（2026-10-11）。実測で代償が出た

**sketch を正確な集合に置き換えて、戻した。**理由は 40 MiB ではなく**不変条件2**。

| | 実測 |
|---|---|
| 27仕様の骨格数の総和 | **330,610**（最大の1仕様が 46,437） |
| 1骨格あたり | **127.4 B**（`sys.getsizeof` の計上値。RSS ではない） |
| 状態量 | sketch **109 KiB** → 正確な集合 **40.2 MiB** |
| 所要時間 | 105秒 → **162秒**（+54%） |
| 骨格数 | 推定539 → **実際536**（sketch は 0.6% 高く出していた） |

**この見積もりを2回外した。**最初に「数十KB〜2MB」と書いたのは `536 × 27 = 14,472`
で計算していたため。**536 は最も厳しい1仕様の数**で、緩い仕様は 46,437 持っている。
実データで検算して初めて 330,610 が出た。**計上値を見ずに掛け算で見積もった結果。**

#### なぜ戻したか：O(1) にできないのは Python のせいではない

**正確な distinct カウントは原理的に状態量が distinct 要素数に比例する。**
Rust で8バイトのハッシュを持てば定数は下がるが、**比例するという性質は変わらない。**
sketch のような確率的構造が存在するのはそのため。

**「Rust なら解決する」とは書かない。**書くと将来もう一度同じ置き換えを試みることになる。

| | 状態量 | 誤差モデル |
|---|---|---|
| HLL sketch | **固定 4,152 B / 仕様** | 相対誤差 1.6% |
| 8バイトハッシュの集合 | 2.5 MiB（ロードファクタ 0.5 で 5.0 MiB） | **64ビット衝突** |
| Python の `set of str` | **40.2 MiB**（実測） | なし |

ハッシュは実測の **8.0倍**下がる。**1桁であって2桁ではない**（最初に「2桁」と書いたのは
10倍以上の誤り）。そして**64ビットハッシュは正確ではない。**

```
330,610件（27仕様の総和）  衝突確率 ≈ 3.0e-9   （約3.4億分の1）
 46,437件（最大の1仕様）    衝突確率 ≈ 5.8e-11  （約171億分の1）
```

無視できる水準だが、**誤差モデルが0から1に増える。**HLL を外す目的が「スケッチ誤差を
判定経路から消す」だったので、ハッシュに置き換えると小さいまま同じ土俵に戻る。
記録するなら「**64ビット衝突の範囲で正確**」と件数ごとの確率を添えて書くこと。

#### 代わりに採った形

```
掃引          sketch（109 KiB、ライブラリの大きさに依存しない）
正確カウント  uncertain 帯の仕様 ＋ frontier 全件（上限8）＋ 推奨される勝者
```

**frontier の上限8は「正確パスの回数」の上限で、「状態量」の上限ではない。**
8セットを同時に持つと `8 × 46,437 × 127.4 B ≈ 45 MB` で、27仕様を正確にしたときと
ほぼ同じになる。**1仕様ずつ走らせて都度捨てることで、ピークは最大の1仕様分
（約 5.6 MiB）に収まる。**不変条件3（演算器とバルクを同時に1つしか持たない）を
第2パスにも適用した形。

代償は I/O が仕様数倍。同時本数 `k` を上げるなら
`k × 最大仕様の骨格数 × 127 B` で予算から逆算する。**発明した重みではなく除算。**

`tests/test_contraindications.py` が構造として固定している — `exact_scaffold_count`
は件数だけを返す（集合が外に出られない）、内包表記の中では呼ばれない（全結果を同時に
持たない）、`FRONTIER` は宣言された定数。

## 過剰ではないもの

**これは記録として残す。**上の指摘が「全部削れ」に読まれると困る。

| | なぜ必要か |
|---|---|
| **拒否の仕組み** | 丸めない・読み替えない・推測しない。これが製品の中身そのもの |
| **`knobs.py` の出自管理** | published / relaxation の区別が、提案の監査を1行で可能にしている |
| **positive control** | 重い判定が計算の故障と同じ顔をする問題への唯一の対策（禁忌79） |
| **inert 検出** | 今日 MW 600 が6比較すべてで何も絞っていないことを、頼まれずに報告した |
| **撤回の記録** | §8 に反証された仮説が反証として残っている。これが無い系は信用できない |
| **`provenance.py`** | ライブラリが入力であることの検査。無かったときに逆の結論を出した実績がある |

## 併せて見つかった重複（過剰実装ではなく、禁忌31と同じ形）

**`py/feasible.py` が降格済みの `py/candidates.py` から SMARTS を2つ import している。**

```python
# py/feasible.py:175
import candidates as candidates_mod
"primary_amine": lambda m: m.HasSubstructMatch(candidates_mod.ENTRY_AMINE),
"basic_nitrogen": lambda m: m.HasSubstructMatch(candidates_mod.BASIC_N),
```

同じパターンが `py/knobs.py` にもある（`ENTRY_PRIMARY_AMINE`、`BASIC_NITROGEN`）。
**一級アミンの定義が2箇所にある。**

禁忌31 は「パーサは1つにする — 同じ修復のコピーが `candidates.py` にあり、ブラケット
順序だけ直して価数修正が入らなかった」と書いてある。**同じファイルで、同じ形。**
片方だけ直したときに静かに食い違う。

`feasible.py` を `knobs.py` 側に寄せれば、製品経路から降格済みモジュールへの依存も
同時に消える。
